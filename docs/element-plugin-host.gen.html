Wine-NSPA – Element-NSPA

This page documents the Element application port that hosts Windows VST2, VST3, and CLAP plugins through JUCE-NSPA and Wine-NSPA while using JACK as the native audio and MIDI transport.

1. Overview

Element-NSPA is a Linux winelib build of Element that hosts Windows plugins in-process through Wine. It is not just “Element built with a different compiler.” The port changes the runtime contract at four surfaces:

  • Windows plugin format selection and scan policy
  • asynchronous plugin instantiation under winelib
  • embedded Win32 editor and dialog behavior inside a native Linux UI tree
  • JACK-first audio and MIDI routing inside the graph itself

The current application layer is also retuned for the same host model:

  • the main window runs under one GL-backed shell
  • internal file choosers replace native OS dialog assumptions under winelib
  • the graph and mixer surfaces use per-node-type accents so Windows plugin formats and JACK-native nodes are legible inside the same graph

2. Why a separate port exists

Upstream Element is not designed around a Linux winelib host for Windows plugins. The application layer still has to make decisions that are more specific than the JUCE framework layer:

  • which plugin formats belong in this process
  • how scan paths should be derived from WINEPREFIX
  • how early the host has to bootstrap wineserver, COM, and Win32 process-class state
  • how plugin editor windows and file choosers should behave once the app is a Linux shell wrapped around Wine-hosted plugin state
  • how JACK MIDI should be treated in the graph when the primary target is a low-latency JACK workflow

That is why this is an application port, not just “JUCE-NSPA plus a build file.”

Concern Generic Element assumption Element-NSPA shape
Plugin target native Linux formats plus platform-native host formats Windows VST2, VST3, and CLAP through winelib + Wine
Scan defaults native host defaults Wine-prefix VST/VST3/CLAP directories are part of the default scan surface
Runtime bootstrap native app bootstrap wineserver pre-warm plus Win32 process-class and OLE init before plugin load
Editor hosting native plugin editor assumptions embedded Wine HWND-backed editor windows in the Linux UI
Dialog model native or OS-host file choosers JUCE-internal choosers embedded on the main window
MIDI shape on JACK builds generic Linux MIDI backends JACK-first native MIDI ports and graph nodes; ALSA is disabled

3. Host bootstrap

Element performs winelib host initialization before plugin code gets a chance to run static constructors.

The current bootstrap does three things:

  1. ensure a wineserver socket exists, spawning wineserver -p if needed
  2. SetPriorityClass(GetCurrentProcess(), REALTIME_PRIORITY_CLASS)
  3. OleInitialize(nullptr)

The order matters.

  • wineserver must exist before the first Win32 call
  • process-class promotion happens before OleInitialize() so any helper threads spawned during COM or plugin initialization inherit the intended Win32 priority class
  • plugin code then sees a valid OLE environment and the correct Wine-NSPA priority mapping before its own initialization tree starts

The wineserver pre-warm is a host-side defensive step. It avoids a cold-start window where the first Wine client in Element’s process tree can race an uninitialized wineserver.

4. Plugin surface and scan policy

The Element port narrows its plugin surface to the Windows formats that make sense inside this winelib host.

Area Current behavior
VST3 enabled
VST2 enabled, using the system Steinberg VST2 SDK 2.4
CLAP enabled under __WINE__ through JUCE-NSPA CLAPPluginFormat
LV2 not registered under __WINE__
LADSPA not registered under __WINE__

The LV2 and LADSPA exclusions are deliberate. They are Linux-native plugin formats, and loading them inside the same winelib process would pull unrelated native plugin trees and their copies of framework globals into the same address space. For this host, that is the wrong process boundary.

4.1 Wine-prefix path discovery

Element augments default scan paths with Windows-plugin directories inside WINEPREFIX.

Current additions are:

  • drive_c/Program Files/Common Files/VST2
  • drive_c/Program Files/Steinberg/VstPlugins
  • drive_c/Program Files/Common Files/VST
  • drive_c/Program Files/Common Files/VST3
  • drive_c/Program Files/Common Files/CLAP
  • drive_c/users/<user>/AppData/Local/Programs/Common/CLAP

The 32-bit Program Files (x86) paths are intentionally not added. This host is x86_64 winelib, so 32-bit plugin DLLs are not loadable here and would only pollute scan results with permanently broken entries.

4.2 CLAP registration under winelib

Under __WINE__, Element uses JUCE-NSPA’s CLAP host format instead of Element’s native Linux CLAP provider.

That split exists to avoid double registration:

  • native Linux CLAP remains the right path for a native Linux Element build
  • winelib Element wants Windows .clap PE DLLs through Wine LoadLibraryW()
  • the winelib build therefore registers CLAPPluginFormat and gates off the native CLAPProvider

The current CLAP scan path is also in-process under winelib. The scanner-worker IPC used for other formats is not yet reliable enough for the Winegcc CLAP path, so CLAP file enumeration and factory probing stay in the main process.

4.3 Asynchronous instantiation

Interactive plugin add is no longer a message-thread synchronous load.

Current shape:

  1. Element requests createGraphNodeAsync
  2. JUCE-NSPA uses its winelib CreateThread worker to perform plugin creation
  3. completion returns to the message thread
  4. Element finalizes the new node in two pieces:
    • message-thread metadata and resetPorts()
    • worker-thread block-hiding/property shaping before attachment

That keeps the UI responsive while large plugin descriptors and port lists are being materialized.

5. JACK-first audio and MIDI graph path

The current Element JACK MIDI implementation is a live part of the host model. This Linux build disables ALSA and uses JACK as the native audio and MIDI transport.

5.1 Timing and data path

JackAudioIODevice::process() is the timing authority. JACK ingress, Element’s audio callback, graph MIDI consumption, and outbound MIDI emission all happen on that same callback thread.

Current inbound shape:

  1. jack_midi_event_get() reads events from each enabled midi_in_N port
  2. Element writes those events into:
    • currentPeriodMidiInput for the graph-wide JACK MIDI ingress
    • currentPeriodMidiInputPerPort[N] for explicit per-port routing
  3. each event keeps jack_midi_event_t::time as its sample offset within the current JACK period
  4. AudioEngine merges the combined buffer into the graph’s top-level MidiBuffer
  5. JackMidiInputNode reads one per-port buffer directly on that same RT thread
  6. MidiEngine callbacks also see the same JACK-period events

Current outbound shape:

  1. the JACK process callback clears and caches every enabled midi_out_N port buffer before the graph runs
  2. JackMidiOutputNode and JackMidiOutputAllNode call writeJackMidiOutput()
  3. writeJackMidiOutput() writes directly to libjack with the caller’s sample offset for the current period
  4. consumeMidiOutputActivity() reports whether any output write landed during that period, which drives the UI Tx indicator

So the current contract is:

  • same-period input
  • same-period output
  • sample offsets preserved in both directions
  • no helper-thread hop
  • no ringbuffer period delay on the normal output path

5.2 Graph exposure and routing

The host exposes JACK MIDI as actual graph topology instead of a hidden device side effect.

Surface Current behavior
Port counts audio and MIDI both use the same Auto / 2 / 4 / 8 / 16 / 32 shape
Input exposure graph-wide combined JACK MIDI input plus one JackMidiInputNode per configured port
Output exposure one JackMidiOutputNode per configured midi_out_N port plus JackMidiOutputAllNode
Port enable state input/output enable masks are atomically read once per JACK period
Graph UI right-click menus expose live midi_in_N / midi_out_N node insertion
Legacy Graph I/O MIDI pseudo-nodes hidden on JACK builds because JACK MIDI nodes are the real routing surface

JackMidiInputNode also has one focused extra behavior: it can optionally translate inbound MIDI Program Change into a message-thread setCurrentProgram() walk over every downstream plugin reachable through MIDI connections. The MIDI Program Change event itself is still forwarded in the RT stream; the extra dispatcher call is additive, not a replacement.

6. Editor, dialogs, and UI layer

The editor path follows JUCE-NSPA’s embedded Win32 GUI model, so plugin editor windows are still real Wine HWND-backed windows inside a Linux UI tree.

Element does not add a second embed protocol on top of that layer. Editor windows inherit JUCE-NSPA’s WineHWNDEmbedComponent, which means:

  • the whole editor thread queue is pumped, not just the top-level HWND
  • mouse and keyboard ranges drain before the general queue
  • the remaining queue uses the same 4 ms budget as JUCE-NSPA
  • SetWindowPos() and XMoveResizeWindow() stay split across Win32 and X11

Element adds application policy on top:

  • the PluginWindow toolbar path is disabled so the embedded editor fills the content area instead of reserving host chrome
  • Open Session, Save As, Import Graph, and Export Graph use JUCE’s internal file chooser with the main content component as the parent
  • the Lua side bypasses glibc’s setjmp macro rewrite so the runtime stays on glibc’s setjmp() instead of resolving into Wine’s MSVCRT _setjmp path

The internal chooser policy matters under winelib:

  • Wine’s IFileDialog path does not surface reliably here
  • KDE / zenity bridges are not the normal path for this binary
  • top-level non-native dialogs come up with poor decoration behavior
  • embedding the chooser on the main window keeps dialog ownership inside the same Linux shell as the rest of the application

6.1 Inherited embed boundary

The application port reuses the JUCE-NSPA embed substrate directly. The split between framework ownership and application ownership is:

Surface Owner Current behavior
Wine HWND creation and X11 child lookup JUCE-NSPA WineHWNDEmbedComponent creates the HWND and resolves wine_x11_window
Embed message and completion edge JUCE-NSPA + Wine-NSPA WM_X11DRV_NSPA_EMBED_WINDOW plus WM_X11DRV_NSPA_EMBED_DONE
Queue pump discipline JUCE-NSPA whole-thread queue, input-first passes, 4 ms general drain
X11/Win32 geometry split JUCE-NSPA + Wine-NSPA SetWindowPos() keeps Wine rects coherent; host keeps X11 parent-relative sizing coherent
Plugin-window chrome and chooser policy Element-NSPA toolbar-free editor shell and in-app file choosers parented on the main content component

6.2 Graph shell and visual system

Element’s UI layer is not just a reskin. The recent changes move the host toward a clearer separation between application shell, graph topology, and plugin format identity.

Current UI-side decisions:

  • the main DocumentWindow uses one GL context for the shell around the graph
  • the app uses a flat dark baseline across menu bar, popup menus, headers, and content panes
  • graph blocks, wires, and channel strips use a shared type-color mapping
  • JACK builds hide the older Graph I/O MIDI pseudo-surfaces and expose JACK MIDI as explicit graph nodes and preference controls instead
  • Audio/MIDI I/O node UX is tightened around inline channels and port-count synchronization

The current accent map is code, not theme metadata:

Surface Accent
Audio I/O green
MIDI I/O and JACK MIDI orange
VST2 indigo
VST3 purple
CLAP cyan
Element-internal nodes pink

7. Relationship to JUCE-NSPA and Wine-NSPA

Element-NSPA sits on top of both framework and runtime layers.

Layer Use in Element-NSPA
JUCE-NSPA winelib build support, VST2/VST3/CLAP Windows-plugin loading, async CreateThread load path, and the bounded input-first WineHWNDEmbedComponent editor layer
Wine-NSPA X11 embed protocol embeds plugin editor HWNDs under Linux host windows while leaving X11 sizing and the consumer pump discipline on the host side
Wine-NSPA Win32 runtime supplies the window/message model, Win32 process priority mapping, and Wine-side plugin module load path
Element-specific JACK layer exposes JACK-native audio and MIDI routing inside the graph on top of the same host process

Element-NSPA therefore is not a thin build wrapper. It is an application port that binds one specific app shell to the JUCE-NSPA framework layer and to the Wine-NSPA runtime rules underneath it.

8. Current scope

Boundary Current behavior
Host architecture Linux-only x86_64 winelib host
Supported Windows plugin formats VST2, VST3, and CLAP
Linux-native plugin formats in this process excluded under __WINE__
Audio and MIDI transport on Linux build JACK
Dialog model JUCE internal choosers parented on the main window
JACK MIDI graph surface graph-wide and per-port input nodes, per-port and broadcast output nodes
Scan path policy 64-bit Windows-plugin directories only

This page therefore describes a specific application-port shape, not a claim that every Element feature or every native-Linux plugin surface should live in the same process as the winelib Windows-plugin host.
